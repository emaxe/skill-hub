# Спецификация: Загрузка расширений в каталог

## Контекст

Skill-Hub CLI позволяет устанавливать расширения из каталога, но обратного процесса — загрузки расширений **в** каталог — нет. Пользователи могут создавать собственные расширения (skills, agents, commands) локально, но для публикации вынуждены вручную клонировать репозиторий каталога, добавлять файлы, обновлять `catalog.json` и создавать PR. Фича автоматизирует этот процесс из TUI.

### Ключевые решения

- **Мультиплатформенность git-хостинга:** поддержка GitHub, GitLab, Bitbucket, Gitea и любых self-hosted решений. Для этого используется универсальный git-подход (`git push` + ссылка для создания PR/MR в браузере).
- **Проверка доступа:** `git push --dry-run` к кешу каталога проверяет write-доступ. Все функции загрузки отображаются только при наличии прав.
- **Батч-загрузка:** несколько выбранных расширений загружаются в одном коммите/PR.
- **Только TUI:** загрузка доступна только из интерактивного интерфейса (без MCP-инструмента).

## Требования

### Проверка доступа

- **REQ-1:** При запуске TUI (или при входе на экран загрузки) CLI выполняет `git push --dry-run` к URL каталога (`registryUrl` из конфига) для проверки write-доступа.
- **REQ-2:** Результат проверки кешируется в рамках сессии TUI (не выполнять повторно при каждом переходе).
- **REQ-3:** Поддержка SSH и HTTPS URL каталога. CLI использует системные git credentials (SSH ключи, credential helpers) — не хранит и не запрашивает токены напрямую.
- **REQ-4:** Все точки входа в загрузку (кнопки, действия) отображаются **только** если проверка доступа прошла успешно.
- **REQ-5:** При неудачной проверке доступа — показывать понятное сообщение с причиной ошибки (нет прав, сетевая ошибка, невалидный URL).

### Экран «Загрузка расширений» (UploadScreen)

- **REQ-6:** Новый pushed screen (по аналогии с DetailScreen), а не отдельная вкладка.
- **REQ-7:** Экран содержит:
  - Переключатель scope: глобальный / проектный (hotkey для переключения).
  - Список расширений на диске в выбранном scope, отсутствующих в каталоге.
  - Чекбоксы для выбора расширений (space — toggle, a — select all).
  - Превью содержимого выбранного расширения (hotkey `c`).
  - Поле заголовка PR (предзаполненное, редактируемое через hotkey `e`).
  - Поле имени ветки (автогенерация, редактируемое через hotkey `b`).
  - Кнопка «Загрузить» (Enter) — запуск процесса.
- **REQ-8:** Список расширений формируется из результата `adapter.scanInstalled()` с фильтрацией по `loadCatalog()` — показываются только те, которых нет в `catalog.json`.

### Именование ветки и PR

- **REQ-9:** Имя ветки автогенерируется по формату: `upload/{username}-{timestamp}` (или аналогичный уникальный формат). Пользователь может отредактировать.
- **REQ-10:** Заголовок PR автогенерируется из списка выбранных расширений (например: `Add skill: git-helper, agent: code-reviewer`). Пользователь может отредактировать.
- **REQ-11:** При открытии ссылки PR/MR в браузере — title и body предзаполняются через URL-параметры (где поддерживается платформой).

### Процесс загрузки

- **REQ-12:** Валидация перед push:
  1. Наличие основного файла расширения (SKILL.md / AGENT.md / COMMAND.md).
  2. Наличие фронтматтера с обязательными полями: `name`, `description`, `version`, `author`.
  3. Уникальность имени в `catalog.json` (нет дубликата).
  4. Имя расширения в kebab-case.
- **REQ-13:** При ошибках валидации — показать конкретные ошибки по каждому расширению, не прерывая выбор (можно снять галочку с проблемного и загрузить остальные).
- **REQ-14:** Процесс загрузки (после валидации):
  1. В локальном кеше каталога (`~/.skill-hub/`) создать новую ветку от `main`.
  2. Скопировать файлы расширений в структуру каталога (`skills/{name}/`, `agents/{name}/`, `commands/{name}/`).
  3. Обновить `catalog.json` — добавить записи для новых расширений.
  4. Сделать `git commit`.
  5. Сделать `git push origin {branch-name}`.
  6. Сгенерировать ссылку на создание PR/MR с предзаполненными title и body.
  7. Вывести ссылку пользователю и предложить открыть в браузере.
- **REQ-15:** После push — вернуть кеш каталога на ветку `main` (`git checkout main`), чтобы не сломать работу остального CLI.

### Точки входа

- **REQ-16:** Из диалога синхронизации (`ExtensionSyncDialog`): если при синхронизации найдены расширения, отсутствующие в каталоге (`inCatalog === false`) — показать кнопку перехода на UploadScreen. При переходе — автоматически выбираются все подходящие расширения в scope проекта.
- **REQ-17:** Из детального просмотра установленного расширения (`InstalledDetailScreen`): если расширение отсутствует в каталоге — показать действие «Загрузить в каталог». При переходе на UploadScreen — это расширение предвыбрано для загрузки.
- **REQ-18:** Прямой вход на UploadScreen через hotkey из основного интерфейса (вкладка Installed).

### Генерация URL PR/MR

- **REQ-19:** Определение платформы по URL каталога:
  - `github.com` → `https://github.com/{owner}/{repo}/compare/main...{branch}?expand=1&title={title}&body={body}`
  - `gitlab.com` (или self-hosted GitLab) → `https://{host}/{owner}/{repo}/-/merge_requests/new?merge_request[source_branch]={branch}&merge_request[title]={title}`
  - Fallback (неизвестная платформа) → вывести инструкцию: «Создайте PR/MR из ветки `{branch}` в `main` вручную»
- **REQ-20:** Body PR содержит: список загруженных расширений (тип, имя, описание), автор, версия.

## Ограничения

- **OGR-1:** Не входит в скоуп: автоматическое создание PR через API (только git push + ссылка).
- **OGR-2:** Не входит в скоуп: MCP-инструмент для загрузки (только TUI).
- **OGR-3:** Загрузка работает только для расширений текущего агента (платформа определяется по `adapter.agentName`).
- **OGR-4:** Не поддерживается загрузка расширений с мульти-файловой структурой (только основной файл SKILL.md/AGENT.md/COMMAND.md). Если у skill есть дополнительные файлы в папке — они **включаются** в загрузку (вся папка расширения).
- **OGR-5:** Не поддерживается fork workflow — пользователь должен иметь direct push access к репозиторию каталога.

## Макеты и референсы

Не применимо (макетов Figma нет). UI строится по аналогии с существующими экранами TUI.

## Кодстайл и конвенции

- **Файлы:** PascalCase для React-компонентов (`UploadScreen.tsx`), camelCase для модулей (`upload.ts`).
- **Хуки:** Префикс `use`, camelCase (`useUploadAccess.ts`).
- **Экспорт:** Именованные экспорты, не default.
- **React/Ink:** `Box`, `Text`, `useInput`, `useEffect`, `useState`, `useCallback`.
- **Клавиатура:** Обработка через `useInput` + `normalizeInput` из `keymap.ts` для поддержки русской раскладки.
- **Документация:** JSDoc на русском для экспортируемых интерфейсов и функций.
- **Комментарии:** Только для неочевидной логики (почему, а не что).
- **Git:** `simple-git` — npm-пакет, уже используется в проекте.
- **CLAUDE.md:** При добавлении CLI-команд или MCP-инструментов — обновить CLAUDE.md и cli/README.md. (В данном случае — MCP не добавляется, но экран TUI стоит упомянуть.)

## Критерии приёмки

1. При запуске TUI выполняется `git push --dry-run` к URL каталога; результат кешируется в сессии.
2. Если доступа нет — все кнопки/действия загрузки скрыты; показано понятное сообщение при попытке доступа.
3. Если доступ есть — на вкладке Installed доступен hotkey для перехода на UploadScreen.
4. UploadScreen показывает расширения на диске, отсутствующие в каталоге, с фильтрацией по scope.
5. Пользователь может: переключать scope, выбирать расширения чекбоксами, просматривать содержимое, редактировать имя ветки и заголовок PR.
6. При подтверждении: валидация → commit → push → ссылка на PR/MR с предзаполненными title и body.
7. После push кеш каталога возвращён на ветку `main`.
8. Из ExtensionSyncDialog: кнопка перехода на UploadScreen с предвыбранными расширениями (scope проекта).
9. Из InstalledDetailScreen: действие «Загрузить в каталог» с предвыбранным расширением.
10. Ошибки валидации показываются по каждому расширению, не блокируя остальные.
11. Поддержка SSH и HTTPS URL каталога (работает через системные git credentials).
12. Ссылка PR/MR генерируется корректно для GitHub и GitLab; для неизвестных платформ — fallback с инструкцией.
13. Тесты: `npm test` проходит без ошибок.
14. Сборка: `npm run build` проходит без ошибок.
